# Задания по лабораторным работам

Все ЛР выполняются на этом же проекте — вы улучшаете его от работы к работе, а не начинаете каждый раз заново. Каждая ЛР проверяется конкретными автоматическими гейтами из `score.json`: название гейта в скобках — это то, что реально смотрит CI.

## ЛР1 — Code smells и базовый рефакторинг (15 баллов)

**Что сделать:**
- Найти и устранить проблемы в пакете `order` (в первую очередь `OrderService`): один метод отвечает сразу за валидацию, расчёт цены, отправку email и запись в БД — разбейте на классы с одной ответственностью.
- Устранить дублирование кода и magic numbers (например, в `PricingCalculator`).
- Не сломать поведение — эталонные тесты должны остаться зелёными.

**Проверяется:** гейт `lab1_style` — в сумме не больше 15 замечаний Checkstyle и PMD по всему проекту, и при этом эталонные тесты поведения (`OrderApiReferenceTest`, `PricingCalculatorReferenceTest`) зелёные. Если отчёт Checkstyle или PMD не сформировался (например, код не компилируется), гейт не засчитывается. Вес — 15/15.

## ЛР2 — Характеризационные тесты и нормализация БД (20 баллов)

**Что сделать:**
- Написать характеризационные тесты для `PricingCalculator`, покрывающие граничные и отрицательные случаи (сейчас покрыт только базовый путь).
- Нормализовать схему БД: вынести повторяющиеся данные клиента из `orders` в таблицу `customers` (имя клиента — в колонку `customers.full_name`), данные товара из `order_items` — в связь с `products`. Написать Flyway-миграцию (`V2__...sql` и далее). Конвенции — в `src/main/resources/db/migration/README.md`.

**Проверяется:**
- `lab2_coverage` — JaCoCo, построчное покрытие всего проекта ≥ 60%. Вес 10/20.
- `lab2_schema` — эталонный тест проверяет схему после всех миграций: есть таблица `customers` с именем клиента (`full_name`, а после ЛР3 — `first_name`/`last_name`), в `orders` и `order_items` нет дублирующихся колонок. Вес 10/20.

## ЛР3 — Эволюция схемы без даунтайма (15 баллов)

**Что сделать:**
- Разбить `customers.full_name` (результат ЛР2) на `first_name`/`last_name` по паттерну expand-contract: сначала добавить новые колонки и параллельно писать в обе версии, заполнить их для существующих клиентов, перевести чтение, и только потом убрать старую колонку — без остановки приложения.
- Миграции ЛР3 оформить по конвенции: `lab3` в описании, не меньше двух, последняя — contract (см. `src/main/resources/db/migration/README.md`).
- Написать собственный нагрузочный тест, который параллельно с накатом миграции шлёт запросы к API и фиксирует отсутствие ошибок (в балл не входит, но нужен для ЛР5 и защиты своей схемы от регрессий).

**Проверяется:** `lab3_migration` — эталонный тест накатывает миграции ЛР3 под параллельной нагрузкой чтения `customers.full_name` и проверяет: ни одной ошибки до contract-шага, после expand колонки `first_name`/`last_name` есть и заполнены, после contract колонки `full_name` нет. Без миграций ЛР3 гейт не засчитывается. Вес 15/15.

## ЛР4 — N+1 и выделение модуля (20 баллов)

**Что сделать:**
- Устранить N+1 в `GET /orders` (используйте `JOIN FETCH` или `@EntityGraph`).
- Выделить модуль `review` так, чтобы он не обращался напрямую к внутренним классам/репозиториям `order` — только через явный интерфейс/сервис (паттерн Strangler Fig).

**Проверяется:**
- `lab4_nplusone` — количество SQL-запросов через статистику Hibernate не превышает порог. Вес 10/20.
- `lab4_architecture` — ArchUnit-тест на отсутствие обратных зависимостей `review → order` (внутренние классы). Вес 10/20.

## ЛР5 — Финальный цикл (30 баллов)

**Что сделать:**
- Довести проект до состояния, где весь пайплайн проверок проходит одновременно.
- Написать тесты, покрывающие логику настолько, чтобы они ловили внедрённые mutation-testing мутации (PIT) в ключевых модулях.

**Проверяется:**
- `lab5_mutation` — mutation score (PIT) для `PricingCalculator` ≥ 60%. Учитываются только ваши тесты: эталонные тесты из пакета `reference` из прогона PIT исключены. Вес 15/30.
- `lab5_reference` — эталонные тесты поведения (`OrderApiReferenceTest`, `PricingCalculatorReferenceTest`) зелёные на финальной версии. Вес 15/30.

Порог зачёта — сумма баллов по всем ЛР ≥ 60. Актуальный статус по каждому гейту смотрите в артефакте `score` последнего запуска в вашей вкладке **Actions**.
